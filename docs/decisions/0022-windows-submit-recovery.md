# Windows 提交后的命令启动与状态恢复诊断

## Context

Windows 上 Harness 执行机器检查或采集候选机械证据时启动 `git`，都可能返回 `EPERM`，仅凭错误码无法区分命令、工作目录和权限问题。这里的 Node 子进程只用于采集 Git/命令事实，不用于启动或驱动模型。锁获取和状态文件原子替换也可能因文件句柄或目录权限短暂失败；原有错误缺少操作对象和恢复路径，用户难以判断提交是否已经持久化以及是否可以安全重试。

## Decision

命令启动失败时保留参数数组、工作目录和错误码的诊断信息；Build 阶段的 `git status`、`git diff` 非零退出也明确标注具体子命令。不启用可能重新解释检查参数的 shell。锁获取和状态替换失败时增加操作上下文与恢复建议；状态替换留下的临时文件继续由下一次加锁清理。错误信息引导用户先查看 status：仅原 operation 仍在 executing 时重交结果，已 blocked 时修复问题后 retry，其余按最新动作继续。

## Consequences

文件占用和权限错误更容易定位，用户无需猜测是否应删除锁目录。Git 仍需由 Windows 当前用户和 Node 进程正常启动；这只影响 Harness 的机械证据采集，不承担语义理解。实现不以 shell 执行来自规格的参数，也不改变机器检查禁止启动 Agent CLI 的规则。
